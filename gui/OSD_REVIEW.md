# OSD review: gui/ (a6400_gui.elf)

Reviewed 2026-10-29 against F:\a6400project at commit `de73e85` (gui/src last changed in `fac1be3`). `gui/a6400_gui.elf` and the root `a6400_gui.elf` are identical. There was no `gui.log` in the folder, so I couldn't check on-camera output.

## How the OSD is drawn

1. **Finding the surface** (`gui/src/fb.c:192-249`). `fb_open` tries `/dev/fb0` first. That open fails on the a6400 (no fbdev driver), so it falls back to `fb_probe_ma_memspace` (`fb.c:122-190`). That function parses `/proc/udm/ma_memspace_info` and collects up to four `type: monolithic` regions of at least 256 KB. If the first two have the same size, it treats them as a double-buffered pair (e.g. 0x23a80000 and 0x23b16000). Resolution and pixel format are guessed from the region size (`fb.c:241-245`), with 640x480 RGBA4444 as the default.
2. **Mapping** (`fb.c:37-118`). Both physical regions are opened with `/dev/mem` and `mmap2`. `-d /dev/mem@0xPHYS[+0xPHYS2][:WxHxFMT[:STRIDE]]` overrides auto-detection.
3. **Claiming a rectangle** (`fb.c:339-400`, `main.c:721-728`). A centred 540x348 window is claimed. Its current pixels are copied from both surfaces into `saved` and `saved2`, and a RAM back buffer `back` is allocated.
4. **Drawing** (`main.c:542-632`). `render_menu` draws only into `back`, using `gfx_fill`, `gfx_frame` and `gfx_text` (`fb.c:515-611`) with an 11x22 DejaVu bitmap font (`font.h`). Colours are packed by `fb_rgb` (`fb.c:481-494`) with alpha forced to fully opaque.
5. **Presenting** (`fb.c:402-424`). Each row of `back` is `memcpy`'d into **both** surfaces. The main loop (`main.c:885-894`) redraws when the state is dirty and otherwise re-copies the whole window every 40 ms. This is the "continuous present" from `5c4e239`, which keeps painting over whatever Sony's GUI engine draws.
6. **Hiding** (`fb.c:426-445`). `fb_restore` writes the saved snapshots back into both surfaces.

## Bugs

Ordered by impact.

| # | Where | Problem | Suggested fix |
|---|---|---|---|
| 1 | `fb.c:240-246` | **The mapping can run past the end of the detected region.** Any monolithic region of 256 KB or more is accepted. If its size isn't one of the four known sizes, the code still assumes 640x480x2 (600 KB) and maps and writes that many bytes. A 256-599 KB region would therefore have `/dev/mem` writes land in whatever physical memory follows it. | Reject the region unless `sz >= stride*h`, and never let `raw_len` exceed `sz`. Also prefer an exact size match over the "first two monolithic" heuristic. Print what was picked and refuse to draw unless `-d` is given. |
| 2 | `fb.c:46` | **The `/dev/mem` mapping is probably cacheable.** On ARM Linux 3.0, `/dev/mem` mappings of memory the kernel treats as RAM are cached unless the file is opened with `O_SYNC`. CPU writes can then sit in the L1/L2 cache, so the display engine (which reads DRAM directly) shows stale or partial rectangles. That fits the flicker that "continuous present" was added to hide. | Open `/dev/mem` with `O_RDWR|O_SYNC`. `rt.h` has no `O_SYNC` define yet; on ARM in 3.0 it is octal `010000`. |
| 3 | `main.c:813-894`, `fb.c:402-424` | **Two writers on one surface.** Sony's Guiengine still owns both buffers and redraws and flips them. This code writes the same pixels into both, about 25 times a second, with no knowledge of which buffer is being scanned out and no vsync. That causes tearing and flicker, about 19 MB/s of uncached copying while visible, and drawing fights whenever Sony repaints (menus, focus boxes, the histogram). | Short term: copy only when dirty, plus a slower keep-alive (e.g. every 250 ms). Longer term: find out which buffer is the front one. One way is to have `info` sample checksums of both surfaces over a few seconds and see which one Sony writes. A cleaner route is the DDS user-draw API in libObj.so (`DdsUserDrawControl`), which exists for exactly this purpose. |
| 4 | `fb.c:426-445`, `main.c:845-849, 876-878` | **Hiding restores a stale snapshot.** `saved` is captured when the menu opens. If Sony's UI changed under the menu in the meantime, the old pixels are pasted back as a "ghost" until Sony happens to repaint that area. | When hiding, write fully transparent pixels (alpha 0 in RGBA4444) instead of the snapshot, so live view shows through until Sony redraws its own items. Or re-read the surface right before each present and only restore regions you didn't paint. |
| 5 | `main.c:629` | **Footer text is cut off.** `"UP/DN:Move  L/R:Change  ENTER:Run  C1:Hide  C2:Quit"` is 51 characters (561 px) but `maxw` is 516 px, so only 46 characters fit and it ends in `C1:Hide  C2`. Long status messages (up to 63 characters) are clipped the same way at `main.c:628`. | Shorten the text (e.g. `"^v Move  <> Change  OK Run  C1 Hide  C2 Quit"`) or draw it with a smaller font. |
| 6 | `main.c:361-366` | **The film stock always loads as PORTRA_400 when the INI has comments.** `find_substr(buf, STOCKS[i])` searches the whole file, and the stock `RITUAL.ini` has the comment line `# Active Film Stock: PORTRA_400, CINESTILL_800T, ...`, so index 0 always matches. `main.c:784` then calls `save_ritual_ini`, which **overwrites `/mnt/RITUAL.ini` with Portra** and loses the user's choice. | Search for `"STOCK=" + name` (like the grain code at `main.c:367-374`), and drop the unconditional save at startup. |
| 7 | `main.c:358-360`, `392-394` | **SD card edits are ignored.** `/tmp/RITUAL.ini` is read first and `/tmp` is persistent flash, so after the first run, edits to the INI on the SD card (which its comments invite) never take effect. The SD copy also gets rewritten without its comments. | Read the SD file first when it exists, or compare modification times. Preserve unknown lines when saving. |
| 8 | `main.c:426-447` | **Background tasks get lost.** ENTER on rows 1-3 stops a running task, but ENTER on row 0 (Shutter) starts a new background task and overwrites `g_bg_pid`. The running intervalometer or bracket is then no longer tracked, can't be stopped from the GUI, and becomes an unreaped zombie. It may also fire at the same time as the new task. | Refuse, or stop the running task first, whenever `g_bg_pid > 0`, on every row that spawns work. |
| 9 | `main.c:480-491` | **A persistent settings write needs only one ENTER.** Row 7 runs `bk.elf w ... && bk.elf s`, which writes Backup settings to NAND. That goes against the project's "zero NAND writes" policy (PROJECT_MEMORY Decisions, 2026-10-26), there's no confirmation, and the status line says "Unlocked 13h rec limit!" even if the command failed. | Require a second ENTER to confirm, show the exit code from `spawn_sh`, and prefer `rec_unlimit.sh` (which has its own checks) over the inline fallback. |
| 10 | `main.c:399-406`, `474-476` | `ensure_ritual_daemon` runs on startup and on every ENTER on rows 5 and 6. It calls `killall`, which BusyBox 1.13.4 on the camera doesn't have (the error is hidden). It is harmless while `pidof` works, but if the pid file is missing while the daemon runs, the old daemon is never killed. | Use `kill $(cat /tmp/ritual_daemon.pid)` instead of `killall`. |
| 11 | `main.c:179-183` | If writing to `/proc/udm/input` fails once, the loop breaks but `proc_ready` stays 1, so the code never falls back to `/proc/input`. Each poll also does 16 opens of the proc file every 40 ms. | Reset `proc_ready` on failure. If the input driver supports a multi-key dump (`table`), use it to read all keys in one go. |
| 12 | `main.c:845-847` | The return value of `claim_menu_rect` is ignored when re-showing. If it fails, every later present silently does nothing. | Check it and set a status message. |

## Improvements

- **Sony also sees every button press.** Input is only observed (`/proc/udm/input` "get"), not consumed, so MENU, ENTER and the arrows also drive Sony's own UI under the overlay. That causes Sony to repaint (bug 3) and can change real camera settings. Use buttons Sony ignores. In camera settings, set C1/C2 to "Not Set" and use C1 as the "menu mode" toggle. While the menu is open, consider stopping the arrow keys from reaching Sony's UI (there's no way to do that from `/proc` yet, so note it as a limit).
- **Docs and code disagree.** The README key table lists DISP, the control wheel and the front dial as nav keys, and lists MENU/Trash as "hide". In the code, `POLL_KEYS` (`main.c:130-139`) never polls DISP or the wheel codes (`main.c:24, 31-34` are unused), and C2/Trash quits the menu rather than hiding it.
- **Verify colours and pixel format once.** RGBA4444 versus ARGB4444 is inferred, not read from hardware. A one-shot `banner` with pure red, green, blue and white bars would confirm the channel order and alpha polarity (some Sony OSD planes treat alpha 0 as opaque).
- **`info` should say which surfaces it picked and why.** It currently prints the whole memspace file but not the selection reasoning. Log it to `/tmp/gui.log` so a failed run can be diagnosed from the log alone.
- **The Makefile doesn't copy the ELF to the project root** like `build.bat` does, so the two copies can drift apart.
- **Drawing speed is fine.** `gfx_fill` writes 16-bit pixels in a loop, and `memcpy` copies words when aligned. Rows are 1080 bytes (4-byte aligned), so presents use the fast path. The remaining cost is the uncached `/dev/mem` traffic from bug 3, not the drawing itself.
